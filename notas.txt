1. QUÉ ES EL PROYECTO (30 segundos de resumen)
------------------------------------------------------------------
Es un ETL (Extract-Transform-Load: extraer datos de una fuente, transformarlos
a una estructura limpia, y dejarlos disponibles en un formato de salida) escrito
en Python. Extrae los procesos participativos publicados en la Plataforma de
Participación Ciudadana Digital de Uruguay (un sitio construido sobre Decidim,
un software libre de participación ciudadana usado por varios gobiernos) y los
vuelca a un archivo JSON con una estructura fija de 7 campos + 1 opcional.

Se hace por scraping (extracción automática de datos leyendo y parseando el
HTML de las páginas, en vez de usar una API oficial) porque se comprobó que
las dos alternativas no sirven para este caso puntual:
  - /open-data/download existe, pero el ZIP que entrega solo trae "meetings"
    (encuentros) y "proposals" (propuestas) con sus comentarios — no trae
    título, fechas ni entidad a nivel de proceso.
  - /api (una API GraphQL — un tipo de API donde el cliente pide exactamente
    los campos que necesita) no está habilitada en esta instancia del sitio.

2. FLUJO DE EJECUCIÓN, DE PUNTA A PUNTA
------------------------------------------------------------------
Comando de referencia: python main.py --state all --limit 30

Paso a paso:

1. main.py parsea los argumentos de la CLI (--limit, --state, --output) con
   argparse, configura el logging, y llama a crawl(state, limit). No tiene
   lógica de negocio propia — es un orquestador delgado.

2. crawler.py:
   a) listar_slugs() pide /processes?filter[with_date]={state}&per_page=100&page=N
      y extrae los slugs (identificador legible que aparece en la URL, ej.
      "plan-juventudes-2025-2030") del listado con BeautifulSoup (una librería
      para parsear HTML y navegarlo como un árbol de nodos). Deduplica ahí
      mismo con un dict que preserva el orden de inserción. Sigue subiendo
      "page" hasta juntar el --limit pedido o hasta que una página no traiga
      slugs nuevos.
   b) build_proceso(slug) hace el fetch de /processes/{slug} con reintentos,
      y llama a parser.parse_ficha() para convertir el HTML en un objeto
      Proceso. Todo el manejo de errores de un proceso individual vive acá:
      un try/except Exception amplio que loguea slug + URL + excepción y
      devuelve None sin tumbar el resto de la corrida.
   c) crawl() itera los slugs, descarta los None, devuelve la lista de
      Proceso.

3. parser.py recibe el HTML como string (nunca hace requests — esto es
   deliberado, ver sección 4) y usa selectores CSS (patrones para ubicar
   elementos dentro de un documento HTML, ej. ".hero-text h1") para extraer
   cada campo. Devuelve un modelo Proceso (pydantic) validado.

4. output.py serializa la lista de Proceso a JSON y la escribe a disco con
   pathlib.Path, indentado y con ensure_ascii=False (para que los acentos
   queden legibles en el archivo, no escapados como ó).

3. DECISIONES DE MAPEO (lo que más pesa en la evaluación)
------------------------------------------------------------------
Metodología antes de decidir cualquier regla: descargué las 86 fichas reales
del sitio con un script aparte y las analicé programáticamente (no solo mirando
2-3 a mano) para confirmar con conteos exactos cada supuesto, en vez de asumir
a partir de una muestra chica. Todo el detalle con números está en
documentation.md, Fase 0.

3.1. nombre_largo / nombre_corto
   - nombre_largo sale del <h1> visible (dentro de .participatory-space__hero-text).
     ~16% de las fichas (14 de 86) no tienen ese bloque en absoluto (son
     procesos con una plantilla distinta, de fases en vez de rango de fechas)
     -> fallback a <meta property="og:title"> quitando el sufijo fijo del
     sitio. Esto coincide exactamente con lo que pide el enunciado formal
     ("el <h1> de la ficha / og:title").
   - nombre_corto: no hay un subtítulo/resumen del sitio que sirva como
     fuente alternativa fiable. Sí existe un elemento de "bajada" bajo el
     título (.participatory-space__hero-slogan), pero su contenido es texto
     libre inconsistente: a veces el nombre de una entidad, a veces un
     hashtag de campaña de Twitter/X, a veces un eslogan genérico tipo
     "Cuidamos el mañana" que no resume nada del proceso. No califica como
     el "subtítulo/resumen" que el enunciado permite usar como excepción.
     Entonces: se trunca nombre_largo a 80 caracteres, cortando en el último
     espacio completo (nunca a mitad de palabra) y agregando "…". Validado
     con un caso real de 274 caracteres (ficha "consulta72", sobre el precio
     del gas licuado de petróleo) que muestra por qué el truncado hace falta
     de verdad y no es un caso de laboratorio.

3.2. fechas (fecha_inicio / fecha_fin)
   - El sitio muestra un solo string combinado: "29 sep 2025 / 15 nov 2025"
     (meses abreviados en español, minúsculas, sin punto). Se parsea con un
     diccionario manual de meses (ene..dic) en utils/dates.py, sin depender
     del locale del sistema operativo (el locale es la configuración regional
     del sistema que afecta formato de fechas/números — depender de él hace
     que el mismo código se comporte distinto en máquinas distintas, así que
     se evita a propósito).
   - ~16% de los procesos (los mismos 14 sin hero-text) tampoco tienen este
     bloque de metadata -> fecha_inicio y fecha_fin quedan en null explícito,
     nunca string vacío. Es una plantilla distinta (procesos con fases con
     fecha propia en vez de un rango único), no un error de parseo.

3.3. entidad (Grupo promotor) — LA DECISIÓN MÁS INTERESANTE PARA CONTAR
   - Fuente: el bloque de metadata "Grupo promotor" en la ficha. Ausente en
     ~27% de los procesos (23 de 86) -> null explícito.
   - Historia real (contarla tal cual, muestra criterio):
     1) Revisando el output a mano encontré un caso ("Consulta sobre terapias
        alternativas para el TEA") con entidad: null, pero la página sí
        mostraba "Agencia de Evaluación de Tecnologías Sanitarias del
        Uruguay (AETSU)" justo debajo del título.
     2) Investigué el HTML: esa entidad vive en un elemento de "bajada" del
        título (.hero-slogan), no en el bloque "Grupo promotor". Analicé las
        86 fichas cruzando ambas fuentes: en los 23 casos sin "Grupo
        promotor", ese elemento de bajada sí trae algo que lee como una
        entidad real.
     3) Implementé un fallback (si falta "Grupo promotor", usar la bajada),
        lo probé, y el null de entidad bajó de 23/86 a 0/86.
     4) Al confirmar contra el enunciado formal de la prueba, vi que dice
        textualmente: "Es un campo estructurado real, no texto libre... null
        si falta". Eso es exactamente lo que mi fallback violaba (la bajada
        es texto libre, no estructurado). Reverti el fallback. entidad volvió
        a 23/86 en null, que es el comportamiento correcto y pedido.
   - Por qué contar esto en la sustentación: demuestra que no me quedé con la
     primera lectura del HTML, que investigué con evidencia antes de decidir,
     y que prioricé cumplir la letra del contrato de datos por sobre "mejorar"
     un resultado que técnicamente se podía enriquecer. Es el tipo de criterio
     que la consigna dice que evalúa explícitamente.

3.4. formulario_url y componentes (con múltiples opciones)
   - Selector: a.participatory-space__nav-item (los enlaces bajo "Salta a:"
     en la ficha) — coincide exactamente con el selector que da el enunciado.
   - formulario_url = el primer enlace en el orden en que aparece en el DOM
     (estructura en árbol de un documento HTML). Supuesto documentado: se
     asume que el orden del DOM refleja el orden de prioridad que definió
     quien armó el proceso en el panel de administración de Decidim — no hay
     forma de confirmar esto desde afuera sin acceso a ese panel.
   - 3 escenarios reales confirmados con conteo exacto: 3 fichas sin ningún
     componente (-> null), la mayoría (60/86) con más de uno (hasta 7 en un
     caso), el resto con exactamente uno.
   - componentes (campo opcional): lista completa de esos enlaces (texto +
     URL absoluta), para no perder información cuando hay más de uno.

3.5. slug y descripcion_url
   - No se parsean del HTML: el crawler ya los conoce (el slug viene del
     listado, la URL es la que usó para pedir la ficha), así que se los pasa
     a parser.py como datos simples. Evita depender de un <link
     rel="canonical"> que se confirmó que no existe en ninguna ficha.
   - Hallazgo real: hay slugs con mayúscula (Homicidios, Consulta65...
     Consulta70, quinto-planGA). Decisión: nunca normalizar el slug a
     minúsculas en ningún punto del pipeline — lowercasearlo rompería la URL
     real (dejaría de apuntar a una página que existe) y la deduplicación
     tendría que ser case-sensitive de todas formas.

3.6. Paginación y volumen
   - El listado con filter[with_date]=all trae 86 procesos reales (piso
     pedido: 30). El parámetro per_page acepta hasta 100, así que con un
     solo request ya vienen los 86 — pero el loop de paginación con page=N
     sigue implementado de forma genérica por si el volumen creciera por
     encima de 100 en el futuro. El enunciado formal habla de "24 por
     página"; lo medido automáticamente da 25 por defecto y hasta 100 con
     el parámetro — una diferencia menor que no cambia el resultado final.

4. ARQUITECTURA DEL CÓDIGO
------------------------------------------------------------------
main.py                 CLI: parsea argumentos, orquesta, sin lógica propia.
config.py                Constantes: URLs, selectores CSS, timeouts, límites,
                         etiquetas de texto a buscar. Nada de "valores mágicos"
                         sueltos en el resto del código.
crawler.py               Listado paginado + build_proceso() por slug.
parser.py                Extracción de campos desde un string de HTML. CERO
                         llamadas de red.
models.py                Proceso / Componente (pydantic) + serialización a
                         dict/JSON.
output.py                Escritura del JSON final (aislado para que cambiar
                         el destino en el futuro, ej. a una base de datos, no
                         toque el resto del pipeline).
utils/http_client.py     Sesión HTTP compartida, reintentos con backoff
                         exponencial, delay entre requests.
utils/dates.py           Diccionario manual de meses es-UY + parseo de fechas.
utils/text.py            Normalización de espacios, separador correcto al
                         extraer texto de nodos anidados, truncado de
                         nombre_corto.
utils/logging_config.py  Configuración del logger en un solo lugar.
tests/                   10 tests contra fixtures HTML reales.

Principios de diseño para poder explicar (y defender) cada pieza por separado:

- parser.py sin I/O (I/O = operaciones de entrada/salida, en este caso red o
  disco): recibe html+slug+url como datos simples y devuelve un modelo. Esto
  es justo lo que permite testear el parser contra un archivo HTML guardado
  localmente, sin red y sin mockear nada (mockear = simular el comportamiento
  de una dependencia externa en un test).
- Manejo de errores "por comportamiento, no por sintaxis": el único
  try/except Exception amplio del proyecto vive en crawler.build_proceso(),
  bien delimitado a un solo proceso, logueado con contexto (slug + URL +
  excepción), y no interrumpe el resto de la corrida. Fuera de ese punto, no
  hay excepciones "tragadas" en silencio en ningún otro lado.
- Reintentos con backoff exponencial (el tiempo de espera entre reintentos
  crece exponencialmente — 0.5s, 1s, 2s — en vez de ser fijo, para no
  insistir agresivamente contra un servidor que ya está teniendo problemas)
  solo ante timeout o error 5xx (errores del lado del servidor). Un error 4xx
  (error del lado del cliente, ej. 404) no se reintenta porque no es un
  problema transitorio que un reintento pueda arreglar.
- Delay fijo entre requests (0.4s) como buena práctica de scraping, no como
  medida "anti-bot" — el sitio no tiene ningún mecanismo de bloqueo que haya
  que esquivar.
- Logging centralizado: se configura una sola vez en main.py
  (utils/logging_config.setup_logging), y cada módulo solo pide su propio
  logger con logging.getLogger(__name__) — evita múltiples configuraciones
  de logging pisándose entre sí.
- Type hints (anotaciones de tipo, ej. "def foo(x: str) -> int") en todas las
  funciones públicas, y pathlib.Path en vez de strings para cualquier ruta de
  archivo.

7. PREGUNTA DE DISEÑO — ETL INCREMENTAL/IDEMPOTENTE
------------------------------------------------------------------
(Idempotente = una operación que, sin importar cuántas veces se ejecute con
la misma entrada, produce siempre el mismo resultado final, sin duplicar ni
corromper nada.)

Resumen de la respuesta completa (documentation.md, Fase 7):
- slug como clave natural de upsert (upsert = "update or insert": si el
  registro ya existe se actualiza, si no existe se inserta) -> INSERT ...
  ON CONFLICT (slug) DO UPDATE en Postgres, o MERGE en otros motores.
- Para no reescribir algo que no cambió: calcular un hash (ej. SHA-256, una
  huella digital corta y determinística de un contenido) sobre los campos
  extraídos, y compararlo contra el hash guardado antes de hacer el UPDATE.
- El sitio no expone updated_at ni sort=updated_at en el listado, así que no
  hay forma de pedir "solo lo que cambió" — igual hay que traer todo el
  listado y las fichas, y es en destino donde se decide qué cambió de verdad.
- La idempotencia ante un corte a mitad de corrida sale gratis de este mismo
  diseño: reprocesar desde cero no duplica nada, cada upsert por slug
  simplemente vuelve a escribir (o no) el mismo registro.

8. PREGUNTAS QUE ME PUEDEN HACER (y cómo responder)
------------------------------------------------------------------

P: ¿Por qué scraping y no la API o los datos abiertos?
R: Se comprobaron las dos vías antes de descartarlas: el ZIP de datos
   abiertos (/open-data/download) solo trae encuentros y propuestas, no
   título/fechas/entidad a nivel de proceso; y el endpoint /api no está
   habilitado en esta instancia (redirige a la home). Ninguna resuelve los
   7 campos pedidos, así que el HTML de cada ficha es la única fuente
   completa.

P: ¿Dónde y cómo se hace la deduplicación por slug?
R: En crawler.listar_slugs(), al armar la lista de slugs, usando un dict que
   preserva el orden de inserción (dict en vez de set porque un set no
   garantiza orden, y el orden de aparición en el listado sí importa para
   respetar --limit correctamente). No se deduplica sobre el resultado
   final: para entonces ya sería tarde, se habría hecho fetch de fichas de
   más.

P: ¿Por qué truncás a 80 caracteres en vez de usar un subtítulo del sitio?
R: Porque el elemento que parece un subtítulo (.hero-slogan) es texto libre
   inconsistente — a veces es la entidad, a veces un hashtag de campaña, a
   veces un eslogan genérico sin relación con el contenido del proceso. No
   es un resumen fiable del título, así que truncar el título completo da
   un resultado más predecible y útil que usar ese campo.

P: Explicá el diseño de reintentos/backoff.
R: 3 reintentos (4 intentos en total) con backoff exponencial: 0.5s, 1s, 2s
   de espera entre intentos. Solo ante timeout o error 5xx (problema del
   servidor, posiblemente transitorio). Un 4xx no se reintenta porque
   reintentar no arregla un error del lado del cliente. Después de una
   respuesta exitosa se aplica además un delay fijo de 0.4s antes del
   siguiente request, como buena práctica de scraping.

P: ¿Por qué el except Exception amplio dentro del loop está bien acá, y en
   qué otro contexto no lo estaría?
R: Está bien acá porque es la ÚNICA forma de cumplir el requisito real: que
   un proceso individual roto (HTML inesperado, timeout persistente, lo que
   sea) no tumbe la corrida completa de 86 procesos. Está acotado a una sola
   función (build_proceso), logueado con contexto completo (slug + URL +
   excepción), y no oculta el error, solo evita que uno malo arruine el
   resto. NO estaría bien, por ejemplo, envolver TODO el main() en un
   except Exception genérico sin loguear nada — ahí sí se estaría escondiendo
   errores de programación reales (un typo, un import roto) detrás de un
   "no pasó nada".

P: ¿Qué pasa si el sitio cambia su HTML mañana?
R: Los selectores viven todos en config.py (un solo lugar), así que un
   cambio de clase CSS implica editar una constante, no buscar por todo el
   código. Si un selector deja de matchear, el campo correspondiente cae al
   null que ya está contemplado en el contrato (o al fallback si lo tiene,
   como nombre_largo) en vez de romper — el pipeline es resiliente a que un
   campo puntual desaparezca, aunque obviamente no puede adivinar una
   estructura completamente nueva sin ajuste manual.

P: ¿Por qué revertiste el fallback de entidad? ¿No era mejorar el dato?
R: (Ver sección 3.3 completa.) Técnicamente sí enriquecía el dato, pero el
   enunciado formal define entidad como "un campo estructurado real, no
   texto libre" con null explícito si falta. El fallback usaba justamente
   texto libre. Prioricé cumplir el contrato de datos tal como está escrito
   en vez de una mejora que el enunciado no pedía y de hecho descarta
   explícitamente.

P: ¿Cómo elegiste pydantic en vez de dataclass?
R: pydantic valida tipos en el borde (cuando el parser arma el objeto)
   sin código manual, y da serialización a dict/JSON gratis (model_dump).
   Con dataclass hubiera tenido que escribir a mano la validación y el
   to_dict().

P: ¿Cómo generaste los fixtures de test?
R: Descargué HTML real de fichas del sitio (no inventado a mano) elegidas
   específicamente para cubrir los casos borde confirmados en la
   exploración: caso feliz, plantilla sin hero-text, cero componentes, sin
   "Grupo promotor". Es HTML real guardado tal cual, no un mock artificial.

9. GLOSARIO RÁPIDO (para repasar antes de la sustentación)
------------------------------------------------------------------
ETL              Extract-Transform-Load: extraer datos de una fuente,
                 transformarlos, y dejarlos en un destino/formato de salida.
Scraping         Extracción automática de datos leyendo y parseando HTML de
                 páginas web, en vez de usar una API oficial.
CLI              Command Line Interface: interfaz para ejecutar el programa
                 desde la terminal con argumentos (--limit, --state, etc.).
Slug             Identificador legible en una URL (ej. "plan-juventudes-
                 2025-2030"), suele usarse como clave única de un recurso.
DOM              Document Object Model: la estructura en árbol de un
                 documento HTML, donde cada etiqueta es un nodo.
Selector CSS     Patrón para ubicar elementos dentro del DOM (ej.
                 ".hero-text h1" = un <h1> dentro de un elemento con esa
                 clase).
Fixture          Archivo de datos de prueba (acá, HTML real) guardado
                 localmente para que los tests no dependan de la red.
Backoff          Estrategia de espera creciente entre reintentos ante un
                 error, para no insistir agresivamente contra un servidor
                 con problemas.
Idempotente      Una operación que da el mismo resultado final sin importar
                 cuántas veces se repita con la misma entrada.
Upsert           "Update or insert": actualizar un registro si ya existe,
                 insertarlo si no.
Hash             Huella digital corta y determinística de un contenido;
                 sirve para detectar si algo cambió sin comparar el
                 contenido entero.
Type hints       Anotaciones de tipo en las firmas de función (ej. "def
                 foo(x: str) -> int") que documentan y permiten chequeo
                 estático sin cambiar el comportamiento en tiempo de
                 ejecución.
Locale           Configuración regional del sistema operativo (idioma,
                 formato de fecha/número); depender de ella hace que el
                 mismo código se comporte distinto en máquinas distintas.
Mockear          Simular el comportamiento de una dependencia externa
                 (ej. una llamada de red) dentro de un test, para no
                 depender de ella de verdad.

     "86 procesos | entidad null: 23 (27%) | fecha null: 14 (16%) |
      formulario_url null: 3 (3%)"
   Es literalmente lo que ya hiciste a mano para la tabla de
   documentation.md, Fase 5.1 — convertirlo en una función reutilizable
   (ej. output.resumen_nulos(procesos)) que corre siempre, gratis, y muestra
   que pensás en observabilidad de datos, no solo en que el script "corra".

2. SCRIPT DE VALIDACIÓN AUTOMÁTICA DEL output.json (esfuerzo bajo, impacto alto)
   Un script separado (ej. validar_output.py) que corre los mismos checks
   que hiciste a mano en la Fase 5: ¿hay >=30 procesos?, ¿slugs únicos?,
   ¿los 7 campos están en cada registro?, ¿fechas en formato YYYY-MM-DD o
   null?, ¿URLs con forma válida? Esto convierte la validación manual en
   algo repetible y demuestra la misma idea que ya aplicaste, pero
   automatizada — muy alineado con el criterio de evaluación "calidad de
   datos".

3. DEMO DE CARGA IDEMPOTENTE (para la pregunta de diseño de la Fase 7)
   En vez de (o antes de) Postgres, un script aparte que hace upsert por
   slug contra una base SQLite local (sqlite3 viene en la librería estándar
   de Python, cero instalación adicional) usando INSERT ... ON CONFLICT
   (slug) DO UPDATE. Correrlo dos veces seguidas y mostrar que la segunda
   vez no duplica nada. Esto prueba en código la respuesta escrita de la
   Fase 7 en vez de dejarla solo en papel — un evaluador que vea esto va a
   notar la diferencia entre "lo puedo explicar" y "lo hice funcionar".
   Si preferís que sea literalmente Postgres (por currículum, por ejemplo),
   anotalo como un script opcional con sus propias dependencias en un
   requirements-optional.txt, y dejá clarísimo en el README que no hace
   falta para correr el entregable pedido — el enunciado dice explícitamente
   que no se requiere conexión a base de datos.

4. CI CON GITHUB ACTIONS (esfuerzo bajo, buena señal de profesionalismo)
   Un workflow de unas 15 líneas que corra "pytest tests/" en cada push.
   Muy pocos candidatos en una prueba técnica se molestan en esto, y cuesta
   muy poco con la suite de tests que ya tenés.

5. CLASIFICACIÓN TEMÁTICA (salud, educación, tecnología, ...) — la más
   riesgosa de las cuatro, hacerla bien si se hace
   Es la idea con más "wow" pero también la que más fácil se puede ir de
   scope. Recomendación si se implementa: NO usar un modelo de ML ni un LLM
   externo (agrega dependencias pesadas, costo, y resultados no
   deterministas para algo que no pide el enunciado). Mejor: un clasificador
   por palabras clave sobre nombre_largo + entidad (ej. si aparece "salud",
   "hospital", "ASSE" -> categoría "salud"; si aparece "educación",
   "escuela", "ANEP" -> "educación", etc.), expuesto como un campo extra
   claramente opcional (ej. categoria_estimada) y documentado como heurística
   propia, no como algo pedido por el enunciado. Es rápido, explicable en la
   sustentación, y no depende de nada externo.

Con 1 y 2 alcanza para "destacar" sin ningún riesgo de que algo interfiera
con la entrega. 3 y 4 son el siguiente escalón si hay tiempo. 5 solo si sobra
tiempo y se puede explicar bien por qué se hizo con reglas simples y no con
un modelo — un jurado técnico va a preguntar exactamente eso.
